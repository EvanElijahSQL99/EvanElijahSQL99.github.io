Argus, Talos and Neura

AI DBA advisors for SQL Server, Oracle and PostgreSQLGenerative AI · RAG
DBA question→Deterministic checks→Retrieve vendor docs→Claude on Bedrock→Answer with sources

The problem

DBA knowledge lives in a few senior heads, and generic AI answers are too confident to use on production systems.

What I built

  • Three advisors on one shared design, so every engine gets the same kind of help.
  • Rules run before any AI: version end-of-support checks, plan analysis and team standards applied to every request.
  • Grounded answers: retrieval over vendor documentation, with the sources shown so a DBA can verify them.
  • Amazon Bedrock (Claude) as the model, with automatic failover to the Anthropic API.

How it solves the problem

Known issues, such as an unsupported version or a red flag in a query plan, are caught by fixed rules before any AI is involved. Every AI answer cites the vendor page it came from, so a DBA can check it before acting. Junior DBAs get senior-level guidance on demand, and senior DBAs stop being the bottleneck.

Janus

Stablecoin reconciliation: blockchain against the booksTokenization · Controls
Book the entry→Submit transaction→Index blocks→Wait for finality→SQL match→Two-person fix

The problem

Tokenized assets live on a blockchain, but the official record lives in a database. When the two disagree, someone has to find out first.

What I built

  • A demo stablecoin (ERC-20) on a real EVM chain, with the holder register, ledger and cash reserve in PostgreSQL.
  • An indexer that respects finality: nothing settles until 5 blocks deep, and chain reorgs are detected and rolled back.
  • One SQL statement pairs every transfer with its booking and classifies each disagreement.
  • A break queue where an analyst proposes each fix and a controller approves it.

How it solves the problem

Disagreements surface within seconds of a transaction becoming final, not at month-end. Each one arrives with a suggested fix, and nothing changes until a second person approves, so the books stay correct and auditable. An unbacked mint shows up immediately as reserve coverage below 100%.

Atlas

Retiring cold SQL Server data into Apache IcebergLakehouse · Retention
Retention policy→Copy to Iceberg→Verify every row→Approve→Purge source→Query in Athena

The problem

Legacy databases carry years of data nobody reads, paying for storage, backups and licenses. Deleting it safely is the hard part.

What I built

  • Retention written as code, with customers under legal hold never touched.
  • Proof before deletion: each yearly slice is compared by row count, money total and a fingerprint of every row.
  • Purge only after a second person approves, in batches, followed by an index rebuild that returns the space.
  • The archive stays queryable in Athena, with time travel and single-customer restore.

How it solves the problem

Cold data leaves the expensive database only after the archive proves it holds an exact copy, which makes the deletion safe to approve. The source database shrinks, so backups and maintenance get faster, and the history stays available for audits and legal requests at a fraction of the storage cost.

Hermes

Change data capture with automated detectionStreaming · Observability
PostgreSQL WAL→Debezium→Kafka→Stream processor→Metrics and alerts

The problem

DBAs spend nights watching for blocking, long transactions and replication lag that software could detect.

What I built

  • Log-based change capture of every insert, update and delete, with no polling and no application changes.
  • Detection rules for blocking chains, long transactions, replication slot lag, transaction ID age and throughput drops.
  • Each problem opens one alert and resolves it on its own, so on-call engineers aren't paged over and over for the same issue.
  • Visitors can break it on purpose and watch it detect and recover.

How it solves the problem

Problems are detected and alerted within seconds, without anyone watching a dashboard. Because each alert opens once and closes itself when the condition clears, on-call staff respond to real problems instead of noise. The same change stream can also feed analytics and a data lakehouse without adding load to the database.

DBaaS control plane

Self-service database requests with standards built inPlatform · APIs
Request→Standards check→Approval→Provision→Operate and audit

The problem

Ticket queues for routine database work slow teams down, and manual work drifts from standards.

What I built

  • Two REST APIs for PostgreSQL: one provisions, one operates.
  • Standards as code validate every request before it reaches a server.
  • Approval workflows, idempotent requests, time-boxed access grants, backup and restore, and a full audit trail.
  • Blocking-chain analysis with a dry run before any session is terminated.

How it solves the problem

Teams get a database through an API in minutes instead of waiting on a ticket queue, and every request is checked against standards before it runs. Approvals, time-limited access and the audit trail happen automatically, so moving faster doesn't mean giving up control.

How I build

Built to production standards

A project is only useful if it would survive production. These are the practices built into every project here.

Tested end to end

Every project ships with automated browser tests that exercise the real user flow, plus integration tests against real databases. The tests run on the deployed environment, not just a laptop.

Controls designed in

Separation of duties, verification before deletion, audit trails and legal holds are part of the design from the first commit, the way SOX and audit expect them.

Secure by default

Nothing is open to the internet except through the CDN. Servers have no SSH, credentials never live in code, and every demo sits behind authentication.

Cost aware

Static front ends cost cents. Compute runs only while it is being used, and one command starts or stops a whole environment.
